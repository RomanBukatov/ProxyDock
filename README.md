# ProxyDock — Windows Desktop HTTP Proxy Launcher

[![CI](https://github.com/RomanBukatov/ProxyDock/actions/workflows/ci.yml/badge.svg)](https://github.com/RomanBukatov/ProxyDock/actions/workflows/ci.yml)
[![Latest Release](https://img.shields.io/github/v/release/RomanBukatov/ProxyDock?label=release)](https://github.com/RomanBukatov/ProxyDock/releases/latest)

**ProxyDock** — это desktop-приложение для Windows 11 на базе **.NET 10** и **Avalonia UI 12**, предназначенное для запуска отдельных программ через индивидуальные HTTP-прокси **без изменения системного прокси Windows**, реестра, WinHTTP, маршрутизации или глобальных переменных окружения.

Основной сценарий первой версии — **удобный запуск Windows GUI-приложений** (включая предустановленные профили для **Google Antigravity Desktop**, **Claude Desktop** и **Codex Desktop**, а также произвольных `.exe`). Поддержка CLI-программ в интерактивном терминале (`Windows Terminal` / `PowerShell`) сохранена как дополнительная универсальная возможность.

## Ключевые особенности

- **Нулевое вмешательство в систему:** переменные окружения (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `http_proxy`, `https_proxy`, `all_proxy`, `NO_PROXY`, `no_proxy`, а также опциональный `NODE_USE_ENV_PROXY=1` для Node.js v22+/v24+) задаются строго через `ProcessStartInfo.Environment` только для запускаемого дочернего процесса.
- **Одновременная работа с разными прокси:** можно запустить несколько приложений одновременно с разными HTTP-прокси или в режиме **«Без прокси»**.
- **Desktop-first профили и анализ стека:**
  - **Google Antigravity Desktop** — автообнаружение Win32 Electron/Chromium, передача переменных окружения и флага `--proxy-server`.
  - **Codex Desktop** — автообнаружение MSIX App Execution Alias (`OpenAI.Codex_*\chatgpt-desktop.exe`), подтверждённая стратегия запуска при выключенном системном прокси Windows (`HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY`, `NODE_USE_ENV_PROXY=1` и `--proxy-server=http://host:port`) с наследованием окружения дочерними процессами `ChatGPT.exe` и `codex.exe` (`app-server` / `exec-server`), а также поиск уже работающих процессов `ChatGPT.exe` / `Codex.exe`.
  - **Claude Desktop** — автообнаружение MSIX App Execution Alias (`claude-desktop.exe`), передача переменных окружения, `NODE_USE_ENV_PROXY=1` и `--proxy-server=http://host:port` (маршрутизация `NetworkService` проверена технически; статус остаётся `Требует проверки` до реального пользовательского теста чата/Cowork) и поиск уже работающих процессов `Claude.exe`.
  - Автоматический инспектор стека для любого добавленного `.exe` (различает Win32 Electron/Chromium, MSIX App Execution Alias, WebView2 и нативные `.exe` без слепого добавления `--proxy-server`), а также общие параметры `--proxy-server` (Desktop) и `NODE_USE_ENV_PROXY=1` (Desktop и CLI) для любых пользовательских профилей.
- **Умное определение запущенных приложений и бесшовный повторный запуск:** инспекция процессов учитывает MSIX package identity, наличие видимого графического окна, процессы в системном трее и вспомогательные процессы Electron/Chromium (`--type=renderer`, `gpu-process`, `utility`, `crashpad`, companion-бинарники вроде `resources\codex.exe` / `cowork-svc.exe`). По умолчанию повторный запуск выполняется **бесшовно без модального окна** и никогда не завершает чужие процессы; при активном основном экземпляре показывается компактное неблокирующее предупреждение о том, что новые настройки прокси могут не примениться до полного перезапуска. В настройках доступна опция **«Спрашивать подтверждение при повторном запуске приложения»** (выключена по умолчанию).
- **Компактные toast-уведомления:** при успешном запуске отображается компактное всплывающее уведомление (например, `Codex Desktop запущен` / `USA Proxy`), которое не сдвигает карточки и автоматически скрывается через 3 секунды. Ошибки запуска остаются доступными до закрытия вручную, а подробная техническая диагностика (MSIX, PID, процессные детали, стек) сохраняется в истории запусков и окне **«Диагностика»**.
- **Управление прокси и безопасность (DPAPI):**
  - Поддержка нескольких HTTP-прокси, дублирования и профиля по умолчанию.
  - Пароли никогда не сохраняются открытым текстом в JSON, не отображаются в интерфейсе, не включаются в экспорт конфигурации и не попадают в логи (`SecretRedactor`).
  - Для хранения паролей используется **Windows DPAPI** (`ProtectedData` с областью `CurrentUser`).
- **Асинхронная диагностика прокси:** раздельная проверка TCP-подключения и реального HTTPS/HTTP-запроса через явно настроенный `SocketsHttpHandler`, определение кода `407 Proxy Authentication Required`, измерение задержки, определение внешнего IP и возможность отмены проверки.
- **Современный лаунчер с адаптивной сеткой карточек:** каждое приложение — карточка единой высоты с оригинальной иконкой (40–48 DIP), полным названием, назначенным прокси, крупной кнопкой запуска (автоматически отключается при отсутствующем `.exe`/CLI с кнопкой **«Исправить»**) и меню `⋯` (**«Запустить без прокси»**, **«Изменить прокси»**, **«Редактировать»**, **«Открыть расположение файла»**, **«Дублировать»**, **«Диагностика»**, **«Удалить»** — удаляется только профиль в ProxyDock, а не сама программа). Число колонок (1–4) подбирается по ширине окна, в конце сетки — карточка «+» для добавления. Автоматически обнаруженные программы показываются компактным списком и скрываются после добавления.
- **Оригинальные иконки:** для Win32 — встроенная иконка `.exe` высокого разрешения; для MSIX — разбор `AppxManifest.xml` (Square44x44Logo / Square150x150Logo, `scale`, `targetsize`, `unplated` / `lightunplated`) без прав администратора и без обращения к содержимому WindowsApps вне штатных путей пакета; результат кешируется с учётом DPI и темы.
- **Простая форма прокси:** название, Host/IP, Port, логин/пароль и «по умолчанию»; быстрая вставка `IP:PORT` или `http://user:pass@host:port`; кнопка проверки прямо в форме; NO_PROXY, таймаут и URL диагностики — в сворачиваемом разделе.
- **Предсказуемый жизненный цикл:** по умолчанию закрытие окна полностью завершает ProxyDock и не оставляет фоновых процессов; уже запущенные приложения продолжают работать независимо со своим прокси-окружением. Поддержка сворачивания в системный трей и автозапуска Windows доступна опционально в настройках.
- **Изолированный тестовый режим (`--data-dir`):** аргумент `--data-dir <path>` позволяет запускать отдельный экземпляр с собственной директорией конфигурации без влияния на рабочие профили пользователя.
- **Надёжное хранение данных:** атомарная запись JSON в `%LOCALAPPDATA%\ProxyDock\config\`, резервные копии, карантин повреждённых файлов, версионирование схемы, экспорт/импорт без секретов.
- **Локализация:** основной интерфейс на русском языке с возможностью мгновенного переключения на английский (`ru` / `en`) и поддержкой тем `Dark` / `Light` / `System`.

### Автоматические обновления и сохранность данных
- При запуске установленной или portable-версии ProxyDock асинхронно проверяет стабильный канал (`Stable`) на GitHub Releases без блокировки интерфейса и не устанавливает обновления без согласия пользователя.
- При наличии новой версии появляется компактное уведомление с кнопкой **«Подробнее»**, открывающее окно обновления (текущая и доступная версии, release notes, размер, прогресс загрузки, кнопки **«Обновить и перезапустить»**, **«Позже»** и переход на GitHub).
- **Изоляция пользовательских данных:** файлы программы располагаются в `%LOCALAPPDATA%\ProxyDockApp\` (или в вашей portable-папке), а пользовательские данные — строго в `%LOCALAPPDATA%\ProxyDock\` (`config\`, `secrets\`, `logs\`, `backups\`, `runtime\`). Обновление или удаление программы **не затрагивает** приложения, прокси, DPAPI-пароли, настройки и историю.
- **Независимость запущенных программ:** во время обновления и перезапуска ProxyDock уже запущенные через него приложения (Codex Desktop, Claude Desktop, Google Antigravity и др.) продолжают работать.
- **Ручная проверка и сетевые режимы:** в **Настройки → Обновления** можно отключить автопроверку, проверить обновления вручную или выбрать сетевой режим (*Стандартное подключение*, *Прямое без системного прокси* или *Через выбранный HTTP-прокси ProxyDock* — без записи паролей в логи и без изменения системного прокси Windows).

### Безопасность и неподписанные сборки Windows
- Все проверки и загрузки обновлений выполняются только по **HTTPS** с валидацией TLS и ограничением доверенных хостов GitHub; целостность пакетов проверяется механизмом Velopack, а в релизах публикуется `SHA256SUMS.txt`.
- Обратите внимание: `SHA256SUMS.txt` подтверждает целостность файла, но **не является криптографическим подтверждением личности издателя** (Authenticode). Пока релизные сборки не подписаны сертификатом Authenticode, Windows SmartScreen может показывать стандартное предупреждение при первом запуске — это нормальное поведение для неподписанных open-source сборок; поддержка Authenticode-подписи рассматривается для будущих релизов.

## GitHub Actions CI/CD и выпуск релизов

- **CI (`.github/workflows/ci.yml`):** запускается на `push`/`pull_request` в `main` и вручную; выполняет restore, сборку Release, прогон всех детерминированных тестов (`Category!=LocalLive`), сохранение `.trx`-отчёта и smoke-проверку `win-x64` (`--verify-startup`).
- **Release CD (`.github/workflows/release.yml`):** запускается при отправке тега `vX.Y.Z` (или вручную по существующему тегу); проверяет формат SemVer, запрещает перезапись уже существующего стабильного релиза, прогоняет все обязательные тесты, публикует Velopack-пакеты (`Setup.exe`, `Portable.zip`, `.nupkg`, `releases.win.json`, `RELEASES`), standalone EXE и `SHA256SUMS.txt` с правами `contents: write` только у job публикации.

### Создание нового релиза
```powershell
git tag v0.1.0
git push origin v0.1.0
```
Версия сборки (`AssemblyVersion`, `FileVersion`, `InformationalVersion`), пакета Velopack и артефактов автоматически определяется из Git-тега через `Directory.Build.props` (`ProxyDockVersion`).

### Изолированная проверка обновления между двумя версиями (локально)
1. Соберите и упакуйте две тестовые версии (`0.1.0` и `0.1.1`) в локальную папку фида с помощью `dotnet vpk pack --packId ProxyDockApp ... --outputDir <feedDir>`.
2. Распакуйте `ProxyDockApp-win-Portable.zip` версии `0.1.0` в отдельную папку `<installDir>` и подготовьте изолированную папку данных `<dataDir>`.
3. Запустите `<installDir>\ProxyDock.exe --data-dir <dataDir> --test-update-source <feedDir>` — приложение обнаружит `0.1.1`, скачает обновление, перезапустится как `v0.1.1` и полностью сохранит конфигурацию в `<dataDir>`.

├── ProxyDock.slnx

Данные пользователя хранятся в `%LOCALAPPDATA%\ProxyDock\`:

- `config/` — `applications.json`, `proxies.json`, `settings.json`, `history.json`
- `secrets/` — зашифрованные через Windows DPAPI учётные данные прокси (`*.bin`)
- `logs/` — ежедневные журналы работы с фильтрацией секретов
- `backups/` — резервные копии и карантин повреждённых JSON-файлов
- `runtime/` — временные самоудаляющиеся `.ps1`-обёртки для CLI-запуска

## Быстрый старт и использование

### 1. Добавление HTTP-прокси
1. Откройте вкладку **«Прокси-профили»** и нажмите **«+ Новый прокси»**.
2. Укажите название (например, `Proxy A`), `Host` (например, `127.0.0.1` или `proxy.example.com`) и `Port`.
3. При необходимости укажите логин и пароль (пароль сохраняется только в Windows DPAPI).
4. Нажмите **«Проверить»**, чтобы выполнить независимую от настроек Windows проверку:
   - сначала проверяется TCP-доступность порта;
   - затем выполняется запрос к диагностическому HTTPS URL через этот прокси.

### 2. Запуск Desktop-приложений (основной сценарий)

#### Google Antigravity
- Используйте профиль **Google Antigravity** (из блока обнаруженных приложений или через меню **«+ Добавить» → «Google Antigravity»**).
- Приложение автоматически определяется в `%LOCALAPPDATA%\Programs\antigravity\Antigravity.exe` (при нестандартной установке путь можно указать вручную).
- Включены переменные окружения прокси и параметр `--proxy-server=http://host:port` (без передачи логина/пароля в командной строке).

#### Claude Desktop
- Используйте профиль **Claude Desktop** (автообнаружение ищет MSIX App Execution Alias `%LOCALAPPDATA%\Microsoft\WindowsApps\Claude_*\claude-desktop.exe` или классическую установку в `LocalAppData`).
- Передаются переменные окружения (`HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY`), `NODE_USE_ENV_PROXY=1` и флаг `--proxy-server=http://host:port`. Маршрутизация `NetworkService` через прокси проверена технически, однако полная работоспособность чатов/Cowork помечена как **«Требует проверки»** до реального пользовательского теста.
- **Важно:** Claude Desktop может оставаться в системном трее (`Claude.exe`) и содержит фоновую службу `cowork-svc.exe`. Перед запуском через другой прокси полностью закройте Claude Desktop, в том числе из трея.

#### Codex Desktop
- Используйте профиль **Codex Desktop** (автообнаружение ищет MSIX App Execution Alias `%LOCALAPPDATA%\Microsoft\WindowsApps\OpenAI.Codex_*\chatgpt-desktop.exe` или локальную установку).
- Пакет включает оболочку Chromium/Owl (`ChatGPT.exe` / `Codex.exe`), внутренний `codex.exe` (`app-server`, `exec-server`) и службу Windows `codex-windows-sandbox-service.exe`.
- Подтверждённый сценарий при выключенном системном прокси Windows: передаются `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, `NODE_USE_ENV_PROXY=1` и `--proxy-server=http://host:port`. Переменные окружения наследуются через MSIX App Execution Alias основным процессом `ChatGPT.exe` и дочерними процессами `codex.exe`.
- Существующие профили Codex и Claude из конфигурации v1 автоматически мигрируют на v2 при запуске без перезаписи явных пользовательских переопределений (`--proxy-server`, `--no-proxy-server`, пользовательских `NODE_USE_ENV_PROXY` и заметок).

#### Произвольное desktop-приложение и CLI
- Нажмите **«+ Добавить» → «Desktop-приложение (.exe)...»**, выберите `.exe`, при необходимости задайте рабочую директорию, аргументы и дополнительные переменные окружения.
- В редакторе любого профиля доступны переключатели **`--proxy-server=http://host:port`** (для Desktop Electron/Chromium/Owl) и **`NODE_USE_ENV_PROXY=1`** (для любых Desktop и CLI приложений на базе Node.js v22+/v24+).
- Нажмите **«Проверить»**, чтобы увидеть результат анализа (Win32 Electron/Chromium, MSIX, WebView2 или нативное приложение) и рекомендации.

### 3. Запуск без прокси, диагностика и CLI-режим
- В меню дополнительных действий (`⋯`) каждой карточки доступны **«Запустить без прокси»**, **«Изменить прокси»**, **«Редактировать»**, **«Открыть расположение файла»**, **«Дублировать»**, **«Диагностика»** (подробный отчёт по стеку, прокси, обнаруженным процессам и истории запусков) и **«Удалить»** (удаляет только профиль из ProxyDock).
- Для терминальных утилит (`claude`, `codex` и других CLI) выберите тип **CLI (терминал)** — они открываются в отдельном интерактивном окне `Windows Terminal` (или `PowerShell` в качестве fallback) без перенаправления ввода/вывода.

## Ограничения лаунчера и проверка применимости

ProxyDock — это **процессный launcher (уровня `ProcessStartInfo`)**, а не перехватчик трафика уровня ОС (как Proxifier, TUN/VPN или WFP-драйвер):

1. **Успешный старт процесса ≠ гарантия проксирования.** Если стороннее приложение жёстко использует WinINet/WinHTTP или собственный сокет-стек, игнорирующий `HTTP_PROXY`/`HTTPS_PROXY`, или запускается внутри изолированного системного сервиса Windows, ProxyDock не перехватывает его соединения принудительно и честно отражает уровень применимости (`Подтверждено`, `Совместимо`, `Требует проверки`, `Не проверено`).
2. **Авторизация в Chromium `--proxy-server`.** Передача `user:pass` в аргументе командной строки небезопасна и не поддерживается универсально в Chromium/Electron. Для прокси с авторизацией в Chromium-приложениях может потребоваться интерактивный ввод или локальный ретранслятор (например, локальный HTTP-прокси на `127.0.0.1` без пароля, перенаправляющий во внешний прокси).
3. **Уже запущенные single-instance приложения.** Electron/MSIX-клиенты часто передают управление существующему экземпляру, игнорируя переменные окружения нового процесса. Всегда полностью закрывайте целевое приложение (включая значок в трее) перед перезапуском через другой прокси.

## Сборка, тестирование и публикация Release

### Сборка Debug и Release
```powershell
dotnet restore ProxyDock.slnx
dotnet build ProxyDock.slnx -c Debug --no-restore
dotnet build ProxyDock.slnx -c Release --no-restore
```

### Запуск из исходников
```powershell
dotnet run --project src/ProxyDock.App/ProxyDock.App.csproj -c Release
```

### Запуск автоматических тестов
```powershell
dotnet test tests/ProxyDock.Tests/ProxyDock.Tests.csproj -c Release
```

### Публикация автономного единого EXE (Windows x64, self-contained single-file)
```powershell
dotnet restore src/ProxyDock.App/ProxyDock.App.csproj -r win-x64
dotnet publish src/ProxyDock.App/ProxyDock.App.csproj `
  -c Release `
  -r win-x64 `
  --self-contained true `
  -p:PublishSingleFile=true `
  -p:IncludeNativeLibrariesForSelfExtract=true `
  -p:EnableCompressionInSingleFile=true `
  --no-restore `
  -o publish/win-x64
```

Готовый исполняемый файл появится по пути `publish/win-x64/ProxyDock.exe`.

## Решение распространённых проблем

- **Приложение запустилось, но ходит напрямую без прокси:** проверьте, не висит ли уже старый экземпляр в системном трее (`Antigravity.exe`, `Claude.exe`, `ChatGPT.exe`, `Codex.exe`); закройте его полностью и запустите снова через ProxyDock.
- **Прокси проходит TCP-проверку (`Только TCP`), но не проходит HTTPS:** убедитесь, что прокси поддерживает HTTP/HTTPS `CONNECT`, а не является SOCKS5-сервером или веб-страницей.
- **Код `407` при проверке прокси:** введите актуальные логин и пароль в настройках прокси-профиля.
- **CLI-команда не найдена:** проверьте, что утилита есть в `PATH`, или укажите полный путь к `.exe` / `.cmd` / `.ps1`.
